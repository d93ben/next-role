# Guided onboarding

## Review the materials first

1. Read status, the index, the existing profile, open questions, relevant saved answers, and unprocessed brain-dump notes. Resume any pending review and honor preferences that the user already stated. Use note IDs as sources for supported experience and `brain-dump update` to link the resulting records or explain where the information was saved. Preserve the original wording.
2. Use career materials already present in the conversation or workspace. On a fresh setup with no materials, show the personal dashboard and invite the user to drag any career materials into this chat. Offer current or past résumés, previous cover letters, commendations, LinkedIn exports, performance reviews, and work samples as options. One item is enough. They can also paste their LinkedIn profile text or describe a recent role. The assistant handles filing. Copy accessible originals into `workspace/input/`, preserve existing files when names collide, and run `intake` to index them. Read TXT/MD/CSV/JSON directly. For PDF/DOCX/images, use an available reader and record the extracted text with `intake extract`, the source ID, and the actual extraction method. If a file is inaccessible, ask for pasted text or a readable export in chat. Use the material before asking about search preferences.

When reviewing an old cover letter, distinguish the person's described experience from the employer's requirements and the candidate's aspirations. For a commendation or performance review, preserve who recognized the work, the contribution they described, and any stated outcome. Use those specifics to suggest roles or ask a focused question if attribution is unclear.

When the user provides their first résumé template, including an attachment supplied in response to the template invitation, save it as the workspace default using the template steps in `application.md`. An ordinary résumé or work sample is career material unless the user identifies it as a template. If a template is already saved, continue using it across sessions. Another attachment changes the preference only when the user asks to use it as the new template.

## Propose one search profile

Present the fields together in a short summary. Indicate which details the user already gave you, which are recommendations and why, and which are open. Propose the fields you can support even if some are open.

| Field | How to build the recommendation |
| --- | --- |
| Target roles | Recommend a small, ranked set of role families or titles at the level supported by the user's experience. Explain the connection to specific responsibilities, results, or work samples. Mark a stretch role when useful. |
| Search area | Use the user's stated search area first. Otherwise use the location in their résumé header or contact details. If the résumé gives only work locations, use the most recent identifiable work location. When several cities cluster in one market, use that market and name the cities that led to it. Show the résumé-based area as a working assumption and proceed without a separate confirmation. If there is no usable location or several equally plausible, unrelated markets, ask which area to use when the search needs it. |
| Work arrangement | Use a stated preference or suggest a flexible starting search mix if helpful. Prior remote, hybrid, or on-site work can support a suggestion, while the user's current preference still needs confirmation. Avoid inferring commute radius, relocation, or willingness to go on-site from an address. |
| Compensation | Preserve the user's amount, range or minimum, and any pay period or pay basis they give. Use their specified currency first. When they give an amount without a currency, use the local currency of the selected search area and display its three-letter code. A bare dollar sign can be resolved the same way when the local currency is a dollar. If the area spans different currencies or gives no clear currency, ask only for the missing currency when needed. Leave the amount open until the user supplies or adopts one. A sourced market benchmark may be offered separately. |
| Priorities | Reflect stated interests and suggest possible priorities when the user's career notes or projects show a recurring interest. Label these as suggestions and leave the field open where there is little evidence. |

End with one invitation to review the whole plan, such as “Does this look like a good starting point? Tell me what you’d change, or say ‘looks good’ and I’ll use these suggestions.” When an open item materially changes the search, add a focused question for that item. Defer experience questions until there is a specific gap worth clarifying. A resume or work sample that already answers a question is enough to move on.

For example, a résumé listing Mountain View and Menlo Park gives a starting search area of the San Francisco Bay Area, California. If the user then says “85,000+ and the rest looks good,” record the minimum as `USD 85,000+`. A stated preference for Toronto would make the same amount `CAD 85,000+`, unless the user specifies a different currency.

## Save the review

1. Save actual replies verbatim with `answer add`. Use `profile set` to save the working search area in `preferences.locations` and a supplied pay target with its resolved currency in `preferences.salary`. In the handoff, identify which values were inferred and the résumé or answer they came from. Apply these defaults during intake and when a pay target arrives later. Save other recommendations once the user approves them. A market benchmark stays context unless the user adopts it as a target. Use the handoff for pending proposals and continue work that can proceed without confirmation.
   If the user corrects the market, update the area. Re-evaluate a currency that came from the old market using the original pay wording, show the updated assumption, and keep any explicitly named currency. Keep the original answer intact. If the currency's origin is unclear, clarify before changing an existing target.
2. Save supported profile details with `profile set` and role/project facts with `experience add` and their source IDs. Paid work, volunteering, school projects, caregiving logistics, and independent work may be relevant. Label the context accurately and use only supported dates, credentials, and outcomes. When records conflict, ask about the discrepancy. Record corrections as a new answer with `supersedes` and update affected facts while keeping unchanged fact IDs and submitted archives.
3. Save progress with `memory set`, validate, rebuild, and link the dashboard. Include any focused questions still pending. Resume them in a later session. Once the profile is confirmed, start the search if the user already asked for it. When the user is ready to search and has only requested onboarding, give them a concrete reply they can use, such as "Say 'Find matching jobs' and I'll search using this profile."
